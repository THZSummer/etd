## 1. 概述

### 1.1 一句话描述

> ETD 是一套领域无关的方法论，为任意领域的复杂任务提供动态构建专业协作树的机制，使每个任务在谋定后动的执行与看护中完成。

### 1.2 命名含义

| 字母 | 全称 | 含义 | 核心特点 |
|------|------|------|---------|
| **E** | Expert | 专家分工 | 专业的事交给专业的 AI/人去做 |
| **T** | Tree | 动态协作树 | 根据现实模型动态生成，可生长凋落 |
| **D** | Design | 设计先行 | 谋定而后动，思考规划先于行动 |

**产品副标题**: AI执行 × 人类看护

### 1.3 核心原则

#### 原则一：专业分工

> 专业的事交给专业的 AI/人去做

| 维度 | 说明 |
|------|------|
| **问题来源** | 复杂任务涉及多个专业领域，一人无法精通全部 |
| **解决思路** | 根据任务类型匹配对应领域的专家节点 |
| **价值主张** | 专业保障、效率提升 |

#### 原则二：设计先行

> 谋定而后动，思考规划先于行动

| 维度 | 说明 |
|------|------|
| **问题来源** | 匆忙执行容易走偏，返工成本高 |
| **解决思路** | 每个节点先设计后实施，设计输出需审视通过 |
| **价值主张** | 方向正确、避免返工 |

#### 原则三：双树并行

> AI执行树 + 人类看护树，节点一一对应

| 维度 | AI执行树 | 人类看护树 |
|------|----------|-----------|
| **职责** | 执行任务 | 审视结果 |
| **原则** | 专业事交给专业 AI | 专业事交给专业人 |
| **根节点** | AI协调者 | 人类负责人 |

#### 原则四：领域无关

> 是方法论而非具体解决方案，不绑定特定领域

| 维度 | 传统工具 | ETD |
|------|---------|-----|
| **定位** | 领域特定解决方案 | 领域无关方法论 |
| **树结构** | 固定预设 | 动态生成 |
| **适用范围** | 特定领域 | 任意领域 |

### 1.4 核心目标

#### 目标一：动态建树

> 根据现实世界的团队、项目、领域，生成专业协作树

- 输入：领域定义 + 团队结构 + 项目目标
- 处理：领域解析 → 团队映射 → 组织成型
- 输出：专业协作树

#### 目标二：演进

> 树是活的，随现实变化生长凋落；非必须时允许人工输入，AI需要时可介入

- **生长**：新专家注册 → 节点生成
- **凋落**：专家退出 → 节点淡出
- **适应**：能力变更 → 结构调整

#### 目标三：质量保障

> 每个节点谋定后动，AI执行 + 人类看护双线并行

- 设计阶段：AI设计专家产出 → 人类审视 → 通过后进入实施
- 实施阶段：AI实施专家产出 → 人类审视 → 通过后向上传递

## 2. 用户故事

### 2.1 用户画像

#### 用户类型 A：Solo 开发者

| 属性 | 描述 |
|------|------|
| **背景** | 独立开发者，一人负责项目全流程 |
| **痛点** | 无法保证每个环节的专业度，质量难以保障 |
| **需求** | 通过 AI 专家辅助，每个环节都有专业输出 |

#### 用户类型 B：小型团队负责人

| 属性 | 描述 |
|------|------|
| **背景** | 3-5 人团队，负责项目协调 |
| **痛点** | 任务分配依赖人工协调，效率低 |
| **需求** | 自动将任务分配给合适的团队成员 |

#### 用户类型 C：专业角色成员

| 属性 | 描述 |
|------|------|
| **背景** | 团队中的产品经理/设计师/开发工程师 |
| **痛点** | 需要处理很多非专业领域的问题 |
| **需求** | 只看护自己专业领域的 AI 输出 |

### 2.2 用户故事列表

#### US-001: Solo 开发者寻求专业辅助

> **作为** 一名 Solo 开发者，
> **我想要** 通过配置领域和项目信息，动态生成一棵专业协作树，
> **以便** 在没有真实团队成员的情况下，每个环节都有 AI 专家辅助完成。

**验收标准**:
- 可以配置领域类型（如软件开发、医疗诊断）
- 可以配置项目基本信息
- 系统根据配置生成对应的专家树
- 每个专家节点都有对应的 AI Agent

**优先级**: P0

---

#### US-002: 团队负责人自动分配任务

> **作为** 小型团队负责人，
> **我想要** 将项目任务输入系统后，自动分配给合适的团队成员（人类或 AI），
> **以便** 减少人工协调成本，提高任务分配效率。

**验收标准**:
- 可以注册团队成员及其能力信息
- 可以输入项目任务
- 系统自动匹配最合适的专家节点
- 任务自动分配到匹配的节点

**优先级**: P0

---

#### US-003: 专业角色看护 AI 输出

> **作为** 团队中的专业角色（如产品经理），
> **我想要** 在我专业领域内，审查 AI 专家的输出结果，
> **以便** 确保 AI 输出符合专业标准，质量可控。

**验收标准**:
- 系统向我推送需要审查的 AI 输出
- 我可以查看 AI 输出的完整内容
- 我可以选择通过或打回修改
- 打回时可以选择提供修改意见

**优先级**: P0

---

#### US-004: 树的动态演进

> **作为** 团队负责人，
> **我想要** 当团队成员加入或退出时，协作树能够自动调整，
> **以便** 树结构始终与现实团队保持一致。

**验收标准**:
- 新成员注册时，自动在树中添加对应节点
- 成员退出时，自动调整树结构
- 支持人工确认调整结果

**优先级**: P1

---

#### US-005: 多领域适配

> **作为** 跨领域项目负责人，
> **我想要** 将 ETD 方法论应用到不同领域（如医疗诊断、法律诉讼），
> **以便** 同一套方法论可以服务多个领域的复杂任务。

**验收标准**:
- 可以配置不同领域的专家类型
- 系统根据领域配置生成对应的专家树
- 支持领域特定的任务分解方式

**优先级**: P2

## 3. 功能需求

### 3.1 需求标识符约定

- **FR**: Functional Requirement - 功能需求
- **NFR**: Non-Functional Requirement - 非功能需求
- **EC**: Edge Case - 边界情况

### 3.2 功能需求列表

#### FR-001: 领域模型管理

**需求描述**: 系统应支持定义和管理不同领域的专业角色模型。

**验收标准**:
- 可以创建领域定义，包含领域名称、描述、适用场景
- 可以定义该领域的专业角色类型（如软件开发的 PM、设计、开发、测试）
- 可以定义角色间的层级关系和协作关系
- 支持领域定义的版本管理

**优先级**: P0

**依赖**: 无

---

#### FR-002: 专家节点注册

**需求描述**: 系统应支持专家节点的注册，包括 AI Agent 和人类角色。

**验收标准**:
- 支持注册 AI Agent 专家，包含名称、能力描述、适用领域
- 支持注册人类角色专家，包含姓名、角色、能力标签
- 专家注册时可以选择关联的 LLM Agent（如配置好的 Claude/GPT）
- 支持专家能力的声明和认证
- 支持专家的启用/禁用状态管理

**优先级**: P0

**依赖**: FR-001

---

#### FR-003: 团队结构配置

**需求描述**: 系统应支持配置现实世界的团队结构信息。

**验收标准**:
- 可以创建团队，包含团队名称、描述、所属领域
- 可以将已注册的专家节点分配到团队中
- 可以定义团队内专家的角色和职责
- 支持层级关系定义（如汇报关系）
- 支持团队结构的版本管理

**优先级**: P0

**依赖**: FR-002

---

#### FR-004: 动态树生成

**需求描述**: 系统应根据领域定义、团队结构、项目目标动态生成专业协作树。

**验收标准**:
- 可以输入项目目标、质量要求等信息
- 系统根据领域定义解析需要的专业角色
- 系统根据团队结构映射可用的专家节点
- 系统生成树结构，包含节点层级关系和分工关系
- 支持树的可视化展示
- 支持人工确认或调整生成的树

**优先级**: P0

**依赖**: FR-001, FR-002, FR-003

---

#### FR-005: 任务分配与调度

**需求描述**: 系统应支持任务在专家节点间的分配和调度。

**验收标准**:
- 支持创建任务，包含任务描述、类型、优先级
- 系统根据任务类型匹配最合适的专家节点
- 支持递归向下分配：节点先找专家，找不到自己做
- 支持任务状态的跟踪（待分配、已分配、进行中、已完成）
- 支持任务结果的向上汇聚

**优先级**: P0

**依赖**: FR-004

---

#### FR-006: 设计先行约束

**需求描述**: 系统应支持每个节点先设计后实施的工作流约束。

**验收标准**:
- 每个任务节点分为设计阶段和实施阶段
- 设计阶段产出设计方案（如架构设计、界面设计）
- 设计方案需经过人类审视（如通过、打回修改）
- 设计通过后才能进入实施阶段
- 实施阶段产出实施结果（如代码、文档）
- 实施结果需经过人类审视

**优先级**: P0

**依赖**: FR-005

---

#### FR-007: 双树并行支持

**需求描述**: 系统应支持 AI 执行树和人类看护树的双树并行架构。

**验收标准**:
- 系统同时维护两棵树：AI执行树 + 人类看护树
- 两棵树的节点一一对应
- AI执行树的节点执行具体任务
- 人类看护树的节点审视 AI 的输出
- 支持树间状态的实时同步
- 支持从看护树向执行树发送反馈

**优先级**: P0

**依赖**: FR-004, FR-006

---

#### FR-008: 树的演进机制

**需求描述**: 系统应支持树的动态演进，包括生长、凋落和适应。

**验收标准**:
- **生长**：新专家注册时，自动在树中添加对应节点
- **凋落**：专家退出时，自动调整树结构（标记淡出/任务迁移）
- **适应**：专家能力声明更新时，重新评估其在树中的位置
- 支持演进的人工确认（非必须）
- 支持演进历史的记录和回滚

**优先级**: P1

**依赖**: FR-004

---

#### FR-009: 专家工作台

**需求描述**: 系统应为每个专家节点提供工作界面。

**验收标准**:
- 专家可以查看分配给自己的任务列表
- 专家可以继续向下找专家或自己处理任务
- 支持设计阶段的输出和提交
- 支持实施阶段的输出和提交
- 支持查看人类审视的反馈
- 提供 CLI 和 Web 两种界面

**优先级**: P1

**依赖**: FR-005, FR-006

---

#### FR-010: 多领域适配

**需求描述**: 系统应支持方法论在不同领域的适配。

**验收标准**:
- 支持配置不同领域的专家类型模板
- 支持领域特定的任务分解方式
- 支持领域模板的导入和导出
- 提供软件开发领域的默认模板
- 提供医疗诊断、法律诉讼等领域的示例模板

**优先级**: P2

**依赖**: FR-001

## 5. 技术设计

### 5.1 系统架构

系统采用分层架构设计：

1. **用户层**: CLI 工具 + Web 界面
2. **API 层**: RESTful API + WebSocket
3. **核心服务层**: 领域管理、专家注册、树生成、任务分配、任务管理、演进管理
4. **数据层**: 关系型数据库 + 缓存 + 消息队列
5. **外部集成**: LLM 服务 + 认证服务

### 5.2 核心模块职责

| 模块 | 职责 | 关键能力 |
|------|------|---------|
| **Domain Manager** | 领域模型管理 | 领域定义 CRUD、角色类型管理、领域模板 |
| **Expert Registry** | 专家注册中心 | 专家注册/注销、能力声明、状态管理 |
| **Tree Generator** | 树生成器 | 解析输入、匹配专家、生成树结构 |
| **Task Dispatcher** | 任务分配器 | 任务解析、专家匹配、递归分配 |
| **Task Manager** | 任务管理器 | 任务生命周期、状态跟踪、结果汇聚 |
| **Evolution Manager** | 演进管理器 | 生长/凋落/适应、历史记录、回滚 |

### 5.3 数据模型

核心实体包括：
- **Domain** (领域): 定义业务领域
- **Role** (角色): 领域内的专业角色类型
- **Expert** (专家): 具体的专家节点（AI或人类）
- **Team** (团队): 现实世界团队结构
- **ExpertTree** (专家树): 生成的协作树
- **TreeNode** (树节点): 树中的单个节点
- **Task** (任务): 需要执行的工作单元
- **TaskOutput** (任务输出): 任务的产出物
- **HumanReview** (人类审视): 人类对AI输出的审查
- **EvolutionEvent** (演进事件): 树的变更历史

### 5.4 API 设计

采用 RESTful API 设计，核心资源包括：
- `/domains` - 领域管理
- `/roles` - 角色管理
- `/experts` - 专家管理
- `/teams` - 团队管理
- `/trees` - 树管理
- `/tasks` - 任务管理
- `/outputs` - 输出管理
- `/reviews` - 审视管理

## 6. 边界情况

### 6.1 边界情况列表

#### EC-001: 专家节点匹配失败

**场景**: 任务需要特定能力的专家，但系统中找不到匹配的专家

**处理策略**:
1. 扩大匹配范围（降低匹配阈值）
2. 向上级节点委托
3. 触发专家招募流程
4. 标记为需人工处理

**验收标准**:
- 匹配失败时有明确的降级策略
- 所有路径都有兜底处理
- 人工介入点清晰

---

#### EC-002: 循环依赖检测

**场景**: 树结构配置错误导致循环依赖（A→B→C→A）

**处理策略**:
1. 树生成时进行循环检测
2. 发现循环时抛出错误并记录
3. 提供循环路径的可视化展示
4. 阻止循环树的生成

**验收标准**:
- 循环检测算法正确性
- 错误信息清晰指向问题
- 不会生成无效树结构

---

#### EC-003: 并发任务冲突

**场景**: 同一专家节点被同时分配多个高优先级任务

**处理策略**:
1. 实现任务队列机制
2. 支持任务优先级排序
3. 提供负载均衡策略
4. 支持任务的抢占和恢复

**验收标准**:
- 并发访问数据一致性
- 任务不会丢失
- 优先级得到正确体现

---

#### EC-004: 网络分区容错

**场景**: 分布式部署时出现网络分区

**处理策略**:
1. 实现心跳检测机制
2. 支持分区自愈或优雅降级
3. 保证分区期间数据不丢失
4. 恢复后自动同步数据

**验收标准**:
- 分区期间数据不丢失
- 恢复后数据一致性
- 客户端无感知或优雅提示

---

#### EC-005: 长时间运行任务处理

**场景**: 任务执行时间过长，可能持续数小时甚至数天

**处理策略**:
1. 支持任务断点续传
2. 实现任务状态定期持久化
3. 支持任务的暂停和恢复
4. 提供任务进度实时推送

**验收标准**:
- 系统重启后任务可恢复
- 进度信息准确及时
- 资源占用可控

---

### 6.2 边界情况处理原则

1. **降级优先**: 遇到异常时优先降级而非直接失败
2. **可观测性**: 所有边界情况都需要记录日志和指标
3. **人工兜底**: 机器无法处理时必须有清晰的人工介入路径
4. **快速恢复**: 故障恢复时间纳入核心指标

### 7.2 清晰的 Feature 拆分建议

基于本 spec 的详细分析，建议将 ETD 拆分为 **4 个垂直 Feature**，而非 discovery 阶段的 3 个水平分层 Feature：

#### 拆分方案对比

| 方案 | 结构 | 优点 | 缺点 |
|------|------|------|------|
| **Discovery 原方案** | 水平分层：Registry / Dispatcher / Workbench | 技术边界清晰 | 用户价值不直观，各层强耦合 |
| **Spec 新建议** | 垂直场景：建模 / 生成 / 执行 / 演进 | 用户价值明确 | 需要跨层协调 |

#### 推荐的 4 个垂直 Feature

```
ETD (Expert Tree Design)
│
├── Feature A: 领域建模 (Domain Modeling)
│   ├── 领域定义管理 (FR-001)
│   ├── 角色类型管理 (FR-001)
│   ├── 专家注册 (FR-002)
│   └── 团队配置 (FR-003)
│   
├── Feature B: 树生成 (Tree Generation)
│   ├── 动态树生成算法 (FR-004)
│   ├── 专家匹配算法
│   ├── 树可视化
│   └── 人工确认流程
│   
├── Feature C: 任务执行 (Task Execution)
│   ├── 任务分配 (FR-005)
│   ├── 设计先行工作流 (FR-006)
│   ├── 双树并行支持 (FR-007)
│   ├── 专家工作台 (FR-009)
│   └── 人类审视流程
│   
└── Feature D: 树演进 (Tree Evolution)
    ├── 生长机制 (FR-008)
    ├── 凋落机制 (FR-008)
    ├── 适应机制 (FR-008)
    ├── 演进历史记录
    └── 回滚机制
```

#### 各 Feature 的核心价值

| Feature | 核心价值 | 用户故事 | 估算工作量 |
|---------|---------|---------|-----------|
| A. 领域建模 | 定义"谁是专家" | US-001, US-002 | 2-3 周 |
| B. 树生成 | 创建"协作结构" | US-001 | 3-4 周 |
| C. 任务执行 | 完成"实际工作" | US-002, US-003 | 4-5 周 |
| D. 树演进 | 适应"变化现实" | US-004 | 2-3 周 |

#### 推荐的实现顺序

```
Phase 1: 基础建模 (Week 1-3)
├── Feature A: 领域建模
└── 核心数据模型落地

Phase 2: 树生成 (Week 4-7)
├── Feature B: 树生成
└── 可视化与确认流程

Phase 3: 执行核心 (Week 8-12)
├── Feature C: 任务执行 (MVP 核心)
└── 设计先行 + 双树并行

Phase 4: 演进能力 (Week 13-15)
├── Feature D: 树演进
└── 生产环境就绪
```

### 7.3 为什么不采用 Discovery 的 3 层拆分

| Discovery 原拆分 | 问题 | 本 Spec 的解决 |
|-----------------|------|--------------|
| expert-node-registry | 只解决"注册"，不解决"如何建模领域" | Feature A 包含完整建模 |
| task-dispatcher | 需要树结构才能分配，与 Workbench 强耦合 | Feature C 包含完整执行流 |
| expert-workbench | 独立存在无意义，需要上游数据 | Feature C 的内置组件 |

### 7.4 决策建议

**建议**: 采纳本 spec 提出的 **4 个垂直 Feature 拆分方案**

**理由**:
1. 每个 Feature 都有独立的用户价值
2. 可以独立交付和验证
3. 团队可以并行开发不同 Feature
4. 减少了层间耦合带来的集成风险
